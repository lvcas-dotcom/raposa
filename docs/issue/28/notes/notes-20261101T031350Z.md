# Notas — issue #28 — formato do caso de benchmark e validação

## O que a análise mediu

- `evaluate` decodifica direto nos tipos do domínio, com nomes de campo em pt-BR e
  `command.Decode` recusando campo desconhecido e conteúdo extra (`internal/adapters/command/reviewer.go:43`).
- `domain.sha` já valida SHA completo de 40 ou 64 hex (`internal/domain/evaluation.go`).
- O guarda de arquitetura reprova `net/*` no domínio; validação de URL fica por prefixo.
- O adapter Git resolve commits com `rev-parse --verify` em ambiente isolado e limita a saída a 4 MiB.
- A CLI tem um único nível de comando; `--repo` tem default `.`.

## Decisões

- [usuário] Plano da #28 aprovado com as decisões abaixo.
- Um arquivo por repositório de origem: `Versao`, `Repositorio`, `Licenca` no topo e
  `Casos` dentro. `--repo` aponta para um clone e valida todos os casos do arquivo.
- Nomes do JSON iguais aos campos do domínio, como no `evaluate`.
- Validação acumula todos os problemas com o caminho do campo (`Casos[2].Defeitos[0].Classe`).
- `Limpo: true` exige `Defeitos` vazio e vice-versa.
- Classes: `autenticacao`, `fluxo-de-erro`, `contrato`, `concorrencia`, `dados`, `seguranca`, `logica`.
- `--repo` só verifica quando informado explicitamente (o default `.` não dispara verificação).
- Linhas contadas com `cat-file blob`, que falha se o caminho não for arquivo.
- `resolve` do adapter Git vira `ResolveCommit` exportado em vez de ganhar um wrapper.

## Guardrails

Não executar código do repositório verificado. Não alterar o contrato do `evaluate`.
Exemplo sintético marcado como tal.
